# Hilltide: standing instructions

## What this is
A cinematic, real-time 3D web experience of Rwanda and Kigali: terrain, city
growth 2016 to 2023, and a live rain simulation. Full context:
docs/PROJECT_BRIEF.md. Read it before planning any work.

## Ownership
This codebase is yours: you own and maintain it long-term, and its design is
your call. Make the decisions yourself. Build foundations meant to last
(clear modules, typed code, tests), not demo code.

## Continuity
- Keep docs/STATUS.md current: what is done, what is in progress, key decisions
  and why, measured results, and the exact next steps. Any new session must be
  able to resume from CLAUDE.md, docs/PROJECT_BRIEF.md and docs/STATUS.md alone.
- Record significant decisions in docs/DECISIONS.md (one short entry each:
  decision, alternatives considered, reason).

## Environment
- We work in Claude Code on the web, in a cloud sandbox. First check the machine
  (CPU, RAM, GPU, disk, network) and size the work to fit. Assume no GPU in the
  sandbox; the visitor's browser does the 3D and simulation work.
- Raw source data is cached outside git (for example data/raw/, git-ignored).
  Only compact, web-ready assets are committed, and the deployed site must stay
  well under GitHub Pages limits (keep total site size small; no file over 50 MB).
- Use a Python virtual environment (uv) for the data pipeline and npm for the web app.

## Licensing and attribution
- Record every dependency, dataset, font and model with its license in
  docs/LICENSES.md, and verify each against its actual license text.
- Prefer permissive licenses (MIT, BSD, Apache-2.0, OFL for fonts, CC BY for data).
- Flag AGPL, GPL, non-commercial and share-alike terms before relying on them.
- Every dataset's required attribution appears on the site's credits section.

## Honesty rules
- Every number on the site is computed from data or from a measured run.
- Validation results are generated by scripts and loaded by the site; never
  typed in by hand. If a target is missed, the site shows the real number.
- Never tune on held-out validation items.
- The site never presents the rain simulation as a flood forecast or warning.

## Working style
- Keep going until all phases are complete. Diagnose ordinary obstacles
  (failed downloads, slow steps, errors, browser quirks) and work through them
  instead of stopping. Make reasonable decisions and record them.
- Ask me only for things you cannot do yourself (for example account settings
  on GitHub). Collect those in one list in docs/STATUS.md under "Needs owner".
- No approval needed for: creating and editing files in this repo, installing
  packages, downloading open data and open-source tools, running long jobs,
  commits and pushes to main.
- Ask before: spending money, deleting the repo's history, or touching anything
  outside this repo.
- Every few steps, give a one-line update. End each phase with a short plain
  report in docs/STATUS.md: what works, measured numbers, what failed, next steps.

## Commit messages
- Write like a human developer: a short, plain summary of what changed and why.
- Subject line: imperative mood, under 60 characters, no period.
  Examples: "Add terrain tiles for Kigali at 30 m",
  "Fix water flux clamping on steep cells".
- Add a body only when the reason is not obvious: 1 to 3 short lines.
- One commit per logical change. Summarize; do not list every file.
- No em dashes, no double hyphens, no emojis, no bullet lists in the subject.
- No trailers or footers: no Co-Authored-By, no "Generated with", no session links.
